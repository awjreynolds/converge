# VS Code host integrations for the first Converge client

**Scope:** current, stable VS Code extension APIs and first-party references relevant to issue 4 (checked 2026-08-12).

## Decision

Build the first client as a regular Node-based extension with a `main` entry point and a `contributes.views` Webview View. Treat the extension host as an adapter around the IDE-independent Converge protocol: the webview renders state and emits typed JSON actions; the extension host performs commands, edits, diffs, tasks, terminals, and persistence. This is the smallest boundary that proves the vertical slice without turning Converge into a VS Code-specific core.

Target a trusted, single-folder local workspace in desktop VS Code first. VS Code has local and remote Node extension hosts, while the browser host requires a separate `browser` entry point and has no Node APIs or child-process/executable support. Remote and browser clients are therefore follow-on targets, not assumptions of the first slice. Because Converge executes repository commands, declare restricted-mode behavior explicitly and disable execution when `workspace.isTrusted` is false. ([Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host), [Web Extensions](https://code.visualstudio.com/api/extension-guides/web-extensions), [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust))

## Supported host pattern

| Concern | Supported API/pattern | Boundary implication |
| --- | --- | --- |
| Reasoning panel | Declare a view in `contributes.views`; VS Code activates `onView:${viewId}` when it is opened. Register a `WebviewViewProvider` with `window.registerWebviewViewProvider`. `resolveWebviewView` runs when the view first becomes visible and again after it is shown; the provider owns the HTML and event subscriptions. ([Contribution Points](https://code.visualstudio.com/api/references/contribution-points), [VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Keep a provider instance in the extension host. Treat `resolveWebviewView` as a re-hydration boundary, not a one-time constructor. Do not use a custom editor for the panel. |
| Command handling | Register host commands with `commands.registerCommand`; invoke built-in or extension commands with `commands.executeCommand`. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Webview messages should be a discriminated, JSON-serializable action protocol. Validate the action and authorization in the extension host before side effects. |
| Webview messages | A webview is sandboxed from the extension process. Extension-to-webview uses `webview.postMessage`; webview-to-extension uses `acquireVsCodeApi()` once and `postMessage`. Messages are strings or JSON-serializable values, and extension-to-webview delivery only occurs while the webview is live (visible or retained). ([Webview API](https://code.visualstudio.com/api/extension-guides/webview), [VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Send snapshots/events, not host objects, `Uri`s, DOM objects, or promises. Add an acknowledgement/error message if the UI needs delivery confirmation. |
| Native diff | The built-in `vscode.diff` command accepts left and right resources, a human-readable title, and optional editor options. An extension can supply immutable text at a custom URI through `workspace.registerTextDocumentContentProvider`. ([Built-in Commands](https://code.visualstudio.com/api/references/commands), [VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Register a read-only `converge-snapshot:` provider for the approved baseline and compare that URI with the live workspace-file URI using `executeCommand('vscode.diff', ...)`; the webview only requests `openDiff`. This keeps the comparison valid after the file changes. |
| Workspace edits | `WorkspaceEdit` represents textual and file changes; `workspace.applyEdit` applies edits to one or many resources. Text-only edits use an all-or-nothing strategy. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Keep file mutation in a host-side service. Return the boolean result (or a typed error) to the panel and refresh state from the workspace after applying. |
| Tasks | `tasks.fetchTasks` discovers managed tasks, `tasks.executeTask` starts one, and task lifecycle events report start/end. `executeTask` can fail when a Shell/Process execution cannot start; only `CustomExecution` works in such an environment. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Represent “run verification” as a task request and surface unavailable-process failures as a Change Unit outcome. Do not assume tasks exist or that a shell is available. |
| Terminals | `window.createTerminal` creates an integrated terminal; `Terminal.sendText` sends input and `Terminal.show` reveals it. Shell integration can provide an execution and exit code, but `shellIntegration` may remain unavailable. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api)) | Make terminal use explicit and user-visible. Use shell integration when available; fall back to `sendText` with an “exit status unavailable” result. Never pass untrusted text as a command without an explicit user decision. |

## Webview and Mermaid constraints

JavaScript is disabled by default, so the reasoning UI must opt into `enableScripts: true`. Local scripts, styles, images, and other assets cannot be loaded with `file:` URIs: convert them with `webview.asWebviewUri` and restrict `localResourceRoots`. VS Code recommends a restrictive CSP using `webview.cspSource`, with inline scripts and styles disabled. ([Webview API](https://code.visualstudio.com/api/extension-guides/webview), [VS Code API](https://code.visualstudio.com/api/references/vscode-api))

**Recommendation (inference from those constraints):** bundle Mermaid and its CSS as extension resources, load the bundle through `asWebviewUri`, and use a CSP of the form `default-src 'none'; script-src ${webview.cspSource}; style-src ${webview.cspSource}; img-src ${webview.cspSource};`. Do not use a CDN, inline Mermaid script, workspace asset, or localhost server for the first slice. Initialize Mermaid with `securityLevel: 'strict'` (the default, which encodes HTML and disables click functionality), render only diagram text received over the message channel, and sanitize all other Change Unit text before placing it in HTML. ([Webview API](https://code.visualstudio.com/api/extension-guides/webview), [Mermaid security-level schema](https://mermaid.js.org/config/schema-docs/config-properties-securitylevel.html))

The panel should use the default deallocation lifecycle and persist its model rather than retaining the iframe. `getState`/`setState` preserve JSON-serializable webview state while the view is recreated; `retainContextWhenHidden` keeps scripts running but has high memory overhead and should be reserved for cases where persistence is insufficient. ([Webview API](https://code.visualstudio.com/api/extension-guides/webview), [VS Code API](https://code.visualstudio.com/api/references/vscode-api))

## Persistence choices

- Use `WebviewViewResolveContext.state` plus `acquireVsCodeApi().getState/setState` for the panel’s transient UI state (selected Change Unit, scroll/expansion state, pending input). The editor normally deallocates hidden webview documents and recreates them from persisted state. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api))
- Use `ExtensionContext.workspaceState` for workspace-scoped metadata and `globalState` for machine/user-scoped metadata. Use `storageUri`/`globalStorageUri` with `workspace.fs` for larger JSON/event files; those URI locations may not exist until the extension creates them. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api))
- Keep secrets out of both webview state and ordinary mementos; `ExtensionContext.secrets` is the VS Code API for state independent of the opened workspace that is intended for secrets. ([VS Code API](https://code.visualstudio.com/api/references/vscode-api))

This gives the core an injectable persistence interface and avoids making the core depend on VS Code’s storage layout.

## Testing strategy shaped by the host boundary

1. **Core tests:** run ordinary unit tests against the IDE-independent Change Unit model, reducer, action schema, and persistence interface.
2. **Extension integration tests:** use the official Extension Development Host with `@vscode/test-cli` and `@vscode/test-electron`. Tests have full VS Code API access, can open a fixture workspace, activate the extension, execute commands, assert `WorkspaceEdit` results, and observe task/terminal registrations. ([Testing Extensions](https://code.visualstudio.com/api/working-with-extensions/testing-extension))
3. **Webview tests:** unit-test the pure HTML/snapshot renderer and the typed message reducer outside VS Code; include a host-level smoke test that reveals the contributed view and exercises its commands. The official integration runner gives tests access to the VS Code API, while extensions have no access to VS Code's DOM, so full webview interaction remains a short manual walkthrough for the first slice (including Mermaid rendering and checking Developer Tools for CSP violations). This limitation is an inference from the supported surfaces. ([Testing Extensions](https://code.visualstudio.com/api/working-with-extensions/testing-extension), [Extension Capabilities](https://code.visualstudio.com/api/extension-capabilities/overview), [Webview API](https://code.visualstudio.com/api/extension-guides/webview))
4. **Trust boundary:** add separate host configurations for trusted and untrusted workspaces; VS Code documents that tests cannot programmatically grant or revoke trust. Assert that the panel may render in restricted mode but agent, task, and terminal execution is unavailable. ([Testing Extensions](https://code.visualstudio.com/api/working-with-extensions/testing-extension), [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust))

If browser support is added later, provide a `browser` entry, bundle the extension into a single web-friendly file, use `workspace.fs` instead of Node `fs`, and add `@vscode/test-web` runs. Browser-host tests are a separate constraint because web extensions run in a Browser WebWorker and cannot create child processes. ([Web Extensions](https://code.visualstudio.com/api/extension-guides/web-extensions), [Bundling Extensions](https://code.visualstudio.com/api/working-with-extensions/bundling-extension))

## Local VSIX packaging

Use the first-party `@vscode/vsce` CLI: `vsce package` creates an installable `.vsix`; install it with the Extensions view’s **Install from VSIX…** or `code --install-extension path/to/file.vsix`. A `vscode:prepublish` script is run by the packaging workflow, so the production webview/extension bundle must exist before packaging and must not be excluded by `.vscodeignore`. ([Publishing Extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension), [Bundling Extensions](https://code.visualstudio.com/api/working-with-extensions/bundling-extension))

## Resulting client boundary

The first adapter should expose only these host capabilities to the core: `publishSnapshot`, `onPanelAction`, `openDiff`, `applyWorkspaceEdit`, `runTask`, `openTerminal`, and `read/writeState`. All transport payloads remain plain JSON. VS Code imports, `Uri`s, `WorkspaceEdit`s, terminal/task instances, and webview lifecycle objects stay in the adapter. This boundary directly supports the specified flow—propose, discuss/redirect/approve, apply, inspect a native diff, and verify—while keeping the protocol reusable by a later client.
